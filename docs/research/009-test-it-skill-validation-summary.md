# Research Report: /test-itスキル設計の妥当性検証 — 総合まとめ

## 1. Executive Summary

4つの調査（カンニング問題、spec→テスト自動生成、ITベストプラクティス2025、AIテストワークフロー）を統合し、`/test-it`スキルの設計判断を業界知見と照合した。**7つの設計判断すべてが業界のベストプラクティスと整合**しており、特に「実装コードを見せない」設計はエージェント分離で精度61%→87.8%向上、ファイルアクセス制限でチート率≒0%と強い数値的裏付けがある。追加すべき観点として「モック境界の指針」が浮上した。

## 2. 設計判断の検証結果

### 2.1 裏付けられた設計判断

| 設計判断 | 根拠となる調査結果 | 強度 |
|---|---|---|
| **実装コードを見せない（カンニング防止）** | アクセス制限でチート率≒0%（ImpossibleBench）。分離で精度61%→87.8%。カバレッジ87%でもミューテーションスコア38%（実装見てると検出力が低い） | 最強 |
| **specのGiven/When/Thenベース** | Addy Osmani, Martin Fowler, 技術評論社, Augment Codeが推奨。AIとBDDの親和性が高い。GitHub Spec Kit, Tessl, Kiroも同じアプローチ | 強い |
| **1 featureあたり1-3件** | Vladimir Khorikov「最長正のパス+異常系」。Palantir「少数精鋭」。Testing Trophy/Diamond/Honeycombすべてが「ITを中心に」 | 強い |
| **`tests/integration/<feature>/`配置** | UT=コロケーション、IT=トップレベル分離のハイブリッドが2024-2025業界コンセンサス | 強い |
| **specとの対応コメント** | `// Trace(SPEC:REQ-XXX)`が業界標準。IBM「意図が見えないAIテストの70%を破棄」の対策 | 強い |
| **失敗時のspec照合判断** | AI単独判断は未成熟。「テストがspecに合致→実装を直す。乖離→テストを見直す」が推奨パターン | 中程度 |
| **Agent Teamsの外で実行** | テストエージェントの分離が品質の鍵。同一コンテキストだとテスト設計が実装知識に汚染される | 強い |

### 2.2 追加すべき観点

| 観点 | 内容 | 優先度 | 根拠 |
|---|---|---|---|
| **モック境界の指針** | Khorikov基準: HTTP API=MSWモック、状態管理/ブラウザAPI=実物。子コンポーネントはITでは実物 | **高** | 業界標準化しつつある。モックの境界が曖昧だとITの価値が下がる |
| **ミューテーションテスト** | カバレッジは嘘をつく（87% vs 38%）。テスト品質の事後検証に最も信頼できる指標 | 中 | Meta ACH, Early.ai EQS, MutGenで実用化が進んでいる |
| **プロパティベーステスト** | ランダム入力100回で検証（Kiro方式）。境界値テストの自動化 | 低 | 導入コストが高い。将来フェーズ |
| **学習ループ** | テストレビュー結果をナレッジ蓄積→次回精度向上（LIFULL方式） | 低 | 効果はあるが仕組み構築が必要。将来フェーズ |

### 2.3 Given/When/ThenのAI時代における有効性

| 観点 | 結論 |
|---|---|
| **AIとの親和性** | 高い。自然言語に近い構造化形式でLLMが解釈しやすい |
| **テストコードへの変換** | 機械的（Given→Arrange, When→Act, Then→Assert）。AI変換コストほぼゼロ |
| **トレーサビリティ** | specのどの条件をテストしているか自明。AIが勝手にテスト増減しにくい |
| **BDDフレームワーク不要** | Cucumber等の中間層なしでLLM直接変換が最も効率的 |
| **業界動向** | Augment Code「SDDのspecはBDDシナリオとして実行される」。BDDが「出力フォーマット」に |

**結論: エッジケースもGiven/When/Then形式にすべき。**
