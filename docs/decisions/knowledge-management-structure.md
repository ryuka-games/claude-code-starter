# ナレッジ管理を4フォルダ+追記デフォルトで設計した

> **TL;DR**: フォルダは4つ（research/decisions/inbox/ideas）。追記がデフォルトで200行超えたら分割。frontmatterは3つ（date/source/tags）。ファイル名は内容ベースのslug。認知科学とナレッジ管理の調査結果に基づく設計。

## フォルダ構造は4つで十分な理由

| フォルダ | 何を入れるか |
|---|---|
| `docs/research/` | 調べて得た情報 |
| `docs/decisions/` | 決めたこと+理由 |
| `docs/inbox/` | 外部から来た情報（打合せ、フィードバック） |
| `docs/ideas/` | 自分の思考・アイデア |

**なぜ4つか**: Miller's Law（7±2）、Hick's Lawの知見で4-5フォルダが最適ゾーン。PARA(4), ACE(3+2), Zettelkasten(0), Johnny Decimal(10) — 主要な分類法も全て4-5に収束。フォルダを第一軸、タグを第二軸のハイブリッドがマークダウン+Gitのベスト。

- フォルダ内はフラット。サブフォルダは作らない
- 膨れたら2階層までを限度として整理

## 追記がデフォルト、200行超で分割する理由

同テーマの情報は既存ファイルに追記して育てる。

**なぜ追記がデフォルトか**: Zettelkasten/Evergreen Notes/Obsidian 5年実践の知見が「まず書け、整理は後」で一致。分割のオーバーヘッドは無視できない。Wikipediaも8,000語超まで分割不要。

**分割トリガー**:
1. 200行超（LLMのLost in the Middle問題 + CLAUDE.md推奨サイズ）
2. 明確に独立したサブテーマが発生
3. 他ファイルから頻繁に参照される部分がある

分割時はSummary Style: 元ファイルに要約+リンクを残し、詳細を子ファイルに切り出す。

## ファイル名は内容ベースのslug

`search-requirements.md`のように内容がわかる名前。日付プレフィックス不要。

**なぜ**: 追記が基本だからファイルを日付で分ける意味がない。日付はfrontmatterのdateで持つ。gitコミット日は「上げた日」であって「情報が生まれた日」ではない。

## frontmatterは3つだけ

- **date**: 情報が生まれた日
- **source**: どこから来たか
- **tags**: テーマで横断検索（3-4個が目安）

Obsidianのfrontmatter形式（`tags: [tag1, tag2]`）と完全互換。

## qmdの知見: タグに凝りすぎない

Shopify創業者Tobiが作ったマークダウン検索エンジン（tobi/qmd）の設計思想:

- フォルダのcontext（説明文）+ 見出し構造のほうがタグより検索精度が出る
- 見出し（h1>h2>h3）でチャンク分割するから「ちゃんと見出しを書く」が一番重要
- 特定ツールにロックインしない汎用設計を保つ

## 4フォルダは「素材」、成果物は別フォルダに置く

4フォルダはインプット（素材）の整理。specや記事はアウトプット（成果物）。混ぜない。

```
素材（/noteが管理）         → 成果物（専用スキルが管理）
research/decisions/inbox/ideas → /spec  → specs/features/
                               → /article → docs/articles/
```

**なぜ混ぜないか**: 記事ネタ（`docs/articles/`）を4フォルダに入れようとすると、どのフォルダにも合わない。目的が違うから。4フォルダは「後からspecや記事に使う素材」を蓄積する場所。成果物は専用スキルが専用フォルダに出力する。

## /noteスキル試行で見つかった2つの問題

1. **出力が膨らみすぎる**: 1行メモが36行に展開された → 「入力に見合った出力サイズ」ルール追加
2. **判断の背景が薄い**: 「なぜそう決めたか」が消えていた → 「背景・動機を残す」ルール追加

**なぜこの2つが重要か**: 出力が膨らむと読み返すコストが上がりメモを取る気がなくなる。背景が薄いと同じ議論を繰り返すことになる。
