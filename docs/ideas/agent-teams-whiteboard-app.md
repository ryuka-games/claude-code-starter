# アイデア: Agent Teams ホワイトボード可視化アプリ

Status: idea
Date: 2026-02-21

## きっかけ

- [Happy Elements社のホワイトボード記事](https://zenn.dev/happy_elements/articles/da2dda3618425c) — 共有Markdownファイル（ホワイトボード）でAgent Teamsの協調が大幅改善
- 今のAgent Teamsは「委任モデル」（指示→放置→結果確認）で、途中の経過が見えない
- retro.mdは結論だけ。「なぜそうなったか」の経過が残らない

## コンセプト

Agent Teamsのホワイトボード（共有ファイル）をチャットUIで可視化し、人も参加できるようにする。

### 2つの機能

1. **可視化（リードオンリー）** — ホワイトボードのログをチャット形式で表示。誰が何を書いたか時系列で追える。作業後の振り返りにも使える
2. **参加（双方向）** — 人もホワイトボードに書き込める。エージェントの議論に途中で割り込んで軌道修正できる

### 今との違い

| | 今 | ホワイトボードアプリ |
|---|---|---|
| 人の関わり | 最初に指示 → 最後に確認 | リアルタイムで経過を見て参加 |
| 途中の軌道修正 | Shift+Up/Downで個別に話す（面倒） | チャンネルに書くだけ（全員に届く） |
| 経過の記録 | 消える | ログとして残る |
| イメージ | 個別DM | Slackのオープンチャンネル |

## 仕組み（ざっくり）

```
Agent Teams ←→ whiteboard.md（共有ファイル）←→ ビューアアプリ ←→ 人
```

- Agent Teams側: 起動プロンプトで「ホワイトボードに書け」と指示。決まったフォーマットで書かせる
- アプリ側: whiteboard.mdをwatchしてチャットUIで表示。人の書き込みもファイルに反映
- エージェントは定期的にホワイトボードを読むので、人の書き込みも拾える

### ログフォーマット（案）

```markdown
[FE 10:01] Task 2 実装開始。localStorage使う方針で
[Designer 10:03] アイコンはLucide Reactの Save を推奨。理由: 既存アイコンと統一
[Human 10:05] それでいこう。ただしダークモード対応も忘れずに
[UI/UX 10:18] 確認ダイアログなしで即保存になってる。spec EC-002違反では？
[PM 10:20] UI/UX指摘の通り。FE、確認ダイアログ追加して
```

## ユースケース

- **実装中の軌道修正** — デザイナーの方針提案を見て「そっちじゃなくてこっち」と即座に言える
- **リサーチフェーズ** — デザイナーが参考探してる間にPMとコンセプト相談、みたいな並行会話
- **振り返りのインプット** — ログが議事録として残るので、retro.mdの元ネタになる
- **後からの経緯確認** — 「あの判断どういう経緯だったっけ」を追える

## ホワイトボードの設計

### 理論的背景

- ホワイトボードは「共有メンタルモデル（SMM）の外在化装置」
- エージェントは独立コンテキストを持つためSMMが自然発生しない → ファイルで外に出す
- Happy Elements社の実験で効いてたのは「見ておいてね」が起点。議論じゃなくて共有
  - Agent Aの発見をBが読んで前提にした
  - 用語が統一された
  - 仮説を検証した

### 全体構造

```
[設定]  Goal、Team & Connections、ルール
         → 最初に1回だけ。会議の前提。変わらない

[ホワイトボード]  2つの役割がある
         → 議論ボード: トピック単位で議論 → 決定 → 反映
         → 掲示板: 気づき・情報を全員に共有（議論は発生しない）
```

### 設定（静的）

| 要素 | 役割 | 誰が書くか |
|---|---|---|
| **Goal** | チームが達成すべきこと。specから抜粋 | PM（初期設定） |
| **Team & Connections** | 誰が何を担当、依存関係 | PM（初期設定） |

### ホワイトボードの2つの役割

| | 議論ボード | 掲示板 |
|---|---|---|
| 目的 | 問いに対してみんなで考えて決める | 気づき・情報を全員に共有する |
| 流れ | トピック → 議論 → 決定 → 反映 | 追記のみ。議論は発生しない |
| 共有メンタルモデル | 議論を通じて文脈が揃う | 読むだけで文脈が揃う |
| 例 | 「アイコンどうする？」→ あーだこーだ → PM決定 | 「Safariは5MBまで」「既存アイコンは全部Lucide React」 |

掲示板の情報から「あれ、これおかしくない？」ってなったら → 新しいトピックとして議論ボードに立てる。

### 議論ボードのトピック・ライフサイクル

```
トピック発生（誰かが問いを立てる）
  → 議論（みんなが意見を追記）
  → 決定（PMが結論出す）
  → 反映（担当者がspec・コードに落とす）

※ 決定を覆す場合 → 元トピックに関連づけた新トピックとして立てる
```

例:
```markdown
### トピック1: エクスポートのアイコンどうする？
- [Designer] Saveがいいと思う。既存と統一できる
- [UI/UX] エクスポートならDownloadのほうが直感的では
- [FE] どっちでも実装は変わらない
- [PM] ✅ Downloadに決定
- [FE] コード反映するね

### トピック2: トピック1のアイコン再検討（関連: トピック1）
- [QA] Downloadだとブラウザのダウンロード機能と紛らわしい
- ...
```

### 未解決の設計論点

- ~~**議論ボードと掲示板を1ファイルにするか分けるか**~~ → ステップ2で分離に決定
- **掲示板の肥大化** — 追記のみだと長くなる。古い情報の扱い
- **議論ボードの同時書き込み** — トピック内はappend-onlyだが、PMの決定追記時に競合しないか
- **粒度** — 何でも書くとノイズ。「全員が知るべきこと」のラインをどう引くか
- **将来的にDB化する場合の移行** — ファイルベースで試して、アプリ化時にDBへ

## 課題

- エージェントのホワイトボード読み取り頻度（ポーリング問題）
- 人の書き込みにエージェントが気づくタイミング
- Claude Code側のファイル監視の仕組み
- ホワイトボードが長くなるとコンテキスト圧迫

2. **ログが溜まったらビューアを作る** — 読み取り専用のチャットUI
3. **双方向にする** — 人の書き込み機能を追加

## ステップ1: ファイルベース実装（2026-02-21）

### 実装内容

- `WHITEBOARD.md` テンプレートを作成（[whiteboard-template.md](../guides/whiteboard/whiteboard-template.md)）
- Agent Teams起動プロンプトにPhase 0（ホワイトボード準備）とホワイトボードルールを追加（[agent-teams.md](../guides/agent-teams.md)）

### 設計判断

- **掲示板のみで開始**: 議論ボードは後回し。Happy Elementsで効果が出たのは議論ではなく「情報共有」の方。まず掲示板で試す
- **PM集約方式**: メンバーがPMにSendMessageで報告 → PMがWHITEBOARD.mdに書く → PMが全員に通知。理由: Happy Elementsの実績（リーダー転記方式）、ファイル競合防止、PMはコード書かないので手が空いている
- **1ファイル構成**: ルール + 掲示板を `WHITEBOARD.md` 1ファイルに収めた。初回はシンプルに
- **「ルール」に名称変更**: 「設定」→「ルール」。エージェントにとって「従うべきもの」というニュアンスを明確化

### 後回しにしたこと

- **議論ボード**: 合意形成が必要な場面（「アイコンどうする？」等）で使う想定だったが、まず掲示板の効果を確認してから
- **全員書き込み方式**: PM集約の結果を見て、ボトルネックになるようなら検討

### 未解決（次回のretroで評価）

- 掲示板の肥大化対策
- 粒度のガイドライン（何を書く/書かないの線引き）
- PM集約がボトルネックにならないか

## ステップ2: 汎用化 + 議論ボード追加（2026-02-22）

### 実装内容

- `whiteboard-template.md` をAgent Teams非依存の汎用ガイドに書き換え
- `agent-teams.md` の起動プロンプトからホワイトボード詳細を切り出し、参照に置き換え
- 議論ボードのセクションとトピックフォーマットを追加

### 設計判断

- **汎用化**: ホワイトボードの本質（発見の記録、意思決定の経緯の記録）は1人でも5人でも同じ。変わるのは運用（誰が書くか、通知はどうするか）だけ。汎用ガイドに構造・書き方を、Agent Teams側に固有の運用ルールを分離
- **議論ボード追加**: 掲示板（情報共有）だけでは「判断が必要な場面」をカバーできない。トピック単位で問い→議論→決定→反映のライフサイクルを持たせる
- **2ファイル分離**: `WHITEBOARD.md`（ルール+掲示板）と `DISCUSSIONS.md`（議論ボード）に分離。掲示板は短い追記だけだが、議論ボードはトピックごとに議論が伸びるため、1ファイルだと肥大化してノイズになる
- **掲示板の記入基準を明文化**: 「他の作業に影響する発見」を具体例で示した（技術的制約、specにない前提、手戻りにつながる情報）
- **1エージェント用途の追加**: セッション跨ぎで文脈を引き継ぐ記録装置として、1エージェントでも有用

### 後回しにしたこと

- 議論ボードの実運用検証（Agent Teamsで実際に使ってretroで評価）
- 全員書き込み方式（PM集約の結果を見て判断）

## ステップ3: トピック単位ファイル分割 + specフォルダ配置 + 知見の3層構造（2026-02-26）

### きっかけ

session-list機能のretroから3つの大きな改善提案が出た。

### 実装内容

- `DISCUSSIONS.md`（単一ファイル）→ `discussions/topic-XX-xxx.md`（トピック単位ファイル）に変更
- WHITEBOARD.mdとdiscussions/をプロジェクトルートからspecフォルダ内に移動
- 関係者表にエージェント名（recipient名）列を追加
- Phase 2に「知見の抽出と配置」ステップを追加
- PM完了チェックに知見配置の確認を追加

### 設計判断

- **トピック単位ファイル分割**: session-listのretroで、DISCUSSIONS.mdは実際にはPMが全員の提案を代筆する「意思決定ログ」になっていた。トピック単位ファイルにすれば各メンバーが自分の言葉で直接書ける。異なるトピックは別ファイルなので並列書き込みの競合もない
- **全員一致は掲示板直接記録**: session-listで7トピック中2つ（Homeボタン配置、削除確認文言）は全員一致で議論が発生しなかった。議論ファイルは意見が分かれたときだけ作成すれば十分
- **specフォルダ内配置**: 機能完了時にspec.md/plan.md/tasks.md/WHITEBOARD.md/discussions/retro.mdが1フォルダで完結した記録になる。ルートが汚れない
- **エージェント名の明記**: session-listでDesigner/QAが`recipient: "PM"`で3回送信ミス。関係者表にエージェント名を書けば防げる
- **知見の3層構造**: retroで出た知見を性質で分類して適切な場所に配置する。ルール→CLAUDE.md、環境の事実→ARCHITECTURE.md、機能固有→spec内WHITEBOARD。機能をやるたびにプロジェクトの知識ベースが育つ

### 解決済みの設計論点

- ~~**議論ボードの同時書き込み**~~ → トピック単位ファイルで解決（異なるトピックは別ファイル、同じトピック内はPMが順序制御）
- ~~**全員書き込み方式**~~ → discussions/のトピックファイルには各メンバーが直接書き込める形に変更。WHITEBOARD.mdはPM集約を維持

## ステップ4（予定）: specのNC → discussions/ パイプライン

### きっかけ

node-search機能のAgent Teamsで、PMがspecのNC（NEEDS CLARIFICATION）をそのままdiscussions/のトピックファイルとして事前作成した。チーム開始時点で議論すべきことが明示されてて、PMが「これ議論して」と振るだけで回る。

### 設計方針

NCの本質は「実装前に決めないといけない未決事項」。誰が解決するかは実行者次第。

```
spec: NC を特定する（選択肢付き）
plan: NC を tasks の依存関係として組み込む
      → discussions/ にトピックファイルを事前作成
      → 「Task X は NC-001 の決定に依存」
実装: NC が解決されてから着手
```

解決方法は実行形態で変わる:
- ユーザーが自分で決める → specの段階でNC回答して終わり
- 1エージェント → discussions/にトピック立てて、ユーザーと相談して決定
- Agent Teams → Designer/UI/UXが議論、PMが決定

**重要: planはAgent Teamsに依存しない**。planはNCへの依存関係だけ書く。誰がどう解決するかはplanの責務じゃない。

### 変更予定

| 場所 | 変更 |
|---|---|
| spec skill | NC項目を選択肢（A/B/C）付きで提示。ユーザーが回答してもスキップしてもいい |
| plan skill | 未解決NCがあればdiscussions/にトピックファイルを事前作成。tasks.mdにNCへの依存を記載 |
| whiteboard template | トピック作成トリガーに「specのNCがある場合、事前作成」を追加 |

### 待ち

node-search機能のAgent Teams完了後に実装。実践結果を見てからテンプレートに反映する。

## ステップ5: skill化 + 知見の4層目（2026-02-27）

### きっかけ

node-search retroで「チーム運用ルールの置き場所がない」問題が判明。3層分類（CLAUDE.md / ARCHITECTURE.md / WHITEBOARD）はコーディングと環境しかカバーしておらず、「文言はDesigner/UI/UXで統一してからFEに渡す」のようなチーム運用ルールは行き場がなかった。

### 実装内容

- `template/.claude/skills/agent-teams/` を新規作成（3ファイル構成）
- `docs/guides/agent-teams.md` の起動プロンプトを削除、skill参照に変更
- `docs/guides/whiteboard/` をAI操作用→人向けガイドに変更

### 設計判断

- **skill化**: Agent Teamsの起動プロンプトをskillに変換。`/agent-teams [機能名]` で実行。retro の学びがskill内に蓄積され、次回に自動で引き継がれる
- **3ファイル分離**（公式推奨の500行制限に対応）:
  - `SKILL.md` — ワークフロー司令塔（フェーズ定義、チーム編成、完了チェック）
  - `team-rules.md` — retroから蓄積されたチーム運用ルール（4層目）
  - `whiteboard-template.md` — WHITEBOARD/discussionsの構造・書式・運用ルール
- **参照は1階層のみ**: SKILL.md → team-rules.md, SKILL.md → whiteboard-template.md（公式推奨に準拠）
- **知見の4層構造**: CLAUDE.md（コーディング） / ARCHITECTURE.md（環境） / team-rules.md（チーム運用） / WHITEBOARD.md（機能固有）
- **docs/guides/はガイドのみ**: AI操作用テンプレートはskill内に移動。guides/は「こういう仕組みがあるよ」の人向け説明

### node-search retroからの改善

- discussions/ トピックファイルに `## 決定` セクションを追記するルール
- discussions/ は Phase 0 だけでなく実装中も使うルール
- タスク完了状況・文言変更を掲示板に記録するルール
- レビュー到着順でFEに転送するルール
- FEタスク中間報告・完了報告の定型フォーマット
