Capture and organize: $ARGUMENTS

## Step 1: 入力を理解する

引数がなければ「何を記録しますか？」と聞く。

引数があれば内容を把握する:
- テキストならそのまま読む
- ファイルパスなら読み込む（複数ファイルも可）
- テキスト+ファイルパスの混在もあり得る

**ファイルパスの判定**: パスに`/`か`.md`を含み、かつファイルが存在すればファイルパスとして扱う。それ以外はテキスト。

## Step 2: どこにどう置くか判断する

内容を理解したら、以下を判断する:

### どのフォルダに置くか

| フォルダ | いつ使うか | 性質 |
|---|---|---|
| `docs/research/` | 調べて得た情報 | **育てる**（追記OK、上書きOK） |
| `docs/decisions/` | 決めたこと+理由 | **育てる**（追記OK、上書きOK） |
| `docs/inbox/` | 外部から来た情報（打合せ、フィードバック、指摘） | **記録**（上書き禁止、毎回新規ファイル） |
| `docs/ideas/` | 自分の思考・アイデア | **育てる**（追記OK、上書きOK） |
| `docs/logs/` | 日報、作業ログ、実験メモ、観察ノート | **蓄積**（追記OK、既存部分の編集禁止） |

**3つの性質:**

- **記録型**（inbox/）: 上書き禁止。毎回新規ファイル。日付プレフィックス（例: `2026-03-25-search-meeting.md`）
- **育てる型**（research/decisions/ideas/）: 追記・編集OK。同テーマに追記して育てる。内容ベースslug
- **蓄積型**（logs/）: 同ファイルに追記するが既存部分は編集しない。追記時は日付見出しで区切る。200行超えたら月単位等で分割

1つの入力に**複数テーマや複数の性質が混在していたら、分けて別ファイルに振り分ける**。例えば「今日やったことまとめて」と言われたら:
- リサーチした内容 → research/（育てる型）
- 決めたこと → decisions/（育てる型）
- 打合せで言われたこと → inbox/（記録型）
- やった作業の記録 → logs/（蓄積型）

フォルダをまたいだ振り分けは積極的に行う。1つのフォルダに無理に押し込まない。

### 既存ファイルに追記するか、新規ファイルか

対象フォルダ内のファイルを確認し、同テーマのファイルがあるか探す。ファイル名とfrontmatterのtagsを見て判断する。

- **同テーマのファイルがあり、追記しても200行以下** → 追記
- **同テーマのファイルがない** → 新規作成
- **追記すると200行を超える** → 新規ファイルに分割（Step 4参照）

### 既存ファイルの整理が必要か

既存ファイルが入力として渡された場合、内容に応じて:
- そのまま構造を整理して同じ場所に置く
- 一部を別フォルダに移動
- 一部を新規ファイルに分割
- 複数ファイルなら統合して整理

**迷ったらユーザーに聞く。** フォルダの振り分け、追記か新規か、分割か統合か。

フォルダが存在しない場合は作成する。

## Step 3: ドキュメントを書く

### frontmatter

```yaml
---
date: YYYY-MM-DD  # 情報が生まれた日。明示されなければ今日の日付をデフォルトにする
source: ""        # どこから来たか。内容から推測する（「打合せで〜」なら打合せ、指示がなければ「自分」）
tags: []          # テーマで横断検索（例: [search, v1, auth]）。3-4個が目安
related: []       # 関連ファイルへの相対パス（任意）。入れたら逆リンクも追加する
---
```

### ファイル名
- **小文字、ハイフン区切り（kebab-case）**: `search-requirements.md`
- **英語**: 日本語はH1タイトルに書く
- **50-80文字目安**
- **内容がわかる名前**: ファイル名は「2つ目の検索インデックス」
- 日付プレフィックス不要（dateはfrontmatterにある）

### 本文の構造

**冒頭にTL;DR（1-3行の要約）を必ず入れる。** TL;DRだけ読めば要点がわかる状態にする。

**見出しは内容を語る名前にする。** 「詳細」「その他」は禁止。見出しだけ読んで内容がわかるようにする。

**テーブル・リストを積極的に使う。** 3項目以上の列挙はリスト化。比較はテーブル化。

例:
```markdown
# 検索機能の要件が決まった

> **TL;DR**: 部分一致検索をv1で提供。全文検索はv2。パフォーマンス制約が理由。

## 打合せで全文検索の要望が出た（2026-03-25）

- 全文検索がほしいという要望
- ただしパフォーマンスが心配

## 技術調査で部分一致が現実的と判明（2026-03-28）

| 方式 | 実装コスト | パフォーマンス |
|---|---|---|
| 部分一致 | 低（既存ライブラリ） | 問題なし |
| 全文検索 | 高（Elasticsearch等） | 要検証 |
```

## Step 4: 200行を超えたら分割する

Summary Styleで分割する:
1. 元ファイルに**サマリー + リンク**を残す
2. 詳細を**子ファイル**に切り出す
3. 元ファイルを読むだけで全体像がわかる状態を保つ
4. 子ファイルのfrontmatter: dateとsourceは元ファイルから引き継ぐ。tagsは子ファイルの内容に合わせて調整。relatedに元ファイルへのリンクを入れる

分割前にユーザーに確認する。

## Step 5: タイトルとTL;DRを見直す

追記・整理した場合、タイトルやTL;DRが中身と合わなくなることがある。合わなくなっていたらユーザーに更新を提案する。

## Step 6: 結果を報告する

- 書き込んだファイルのパス
- 新規作成 / 追記 / 整理 / 統合 / 分割
- 付与したtags
- 逆リンクを追加したファイル

## Rules

- **フォルダは5つ**: research, decisions, inbox, ideas, logs
- **育てる型は追記がデフォルト**（research/decisions/ideas）。**記録型は毎回新規ファイル**（inbox）。**蓄積型は同ファイルに追記、既存部分の編集禁止**（logs）
- **フォルダ内はフラット**。サブフォルダは作らない
- **見出しを丁寧に書く**。見出し構造が検索の精度を決める。育てる型の追記時は内容ベース見出し+日付括弧補足（`## 技術調査で判明（2026-03-28）`）。蓄積型は日付見出し（`## 2026-03-28`）
- **tagsは英語、ハイフン区切り、略語禁止**。`auth`ではなく`authentication`。新規タグをつける前に`docs/`配下のfrontmatterをgrepして既存タグを確認し、同じ概念のタグがあればそれを使う
- **迷ったらユーザーに聞く**
- **200行を超えたら分割を提案する**
- **100行を超えたら目次を追加する**
- **入力の情報量に見合った出力サイズにする**。コンパクトに書く
- **判断の背景・動機を残す**。特にdecisionsでは「なぜそう決めたか」を含める
