# ホワイトボード & 議論ボード テンプレート

## セットアップ

機能の **specフォルダ内** に以下を作成する:
1. `WHITEBOARD.md` — ルール（静的）+ 掲示板（最新の事実・決定の一覧）
2. `discussions/` — トピック単位の議論ファイル（意見が分かれたときだけ作成）

```
specs/features/{機能名}/
  spec.md
  plan.md
  tasks.md
  WHITEBOARD.md          ← ここ
  discussions/           ← ここ
    topic-01-xxx.md
    topic-02-xxx.md
  retro.md
```

### WHITEBOARD.mdと議論ファイルの役割

| | `WHITEBOARD.md` 掲示板 | `discussions/topic-XX.md` |
|---|---|---|
| 役割 | 最新の事実・決定の一覧（日常の参照先） | 議論の経緯ログ（後から参照用） |
| 読むタイミング | 作業開始前・レビュー前に必ず読む | 決定の理由を知りたいとき |
| 書き方 | 1行で結論だけ | トピック内で各メンバーが自分の言葉で記入 |
| 作成タイミング | Phase 0で必ず作成 | 意見が分かれたときだけ作成（Phase 0でも実装中でも） |

**全員一致で即決** → 掲示板に直接記録。議論ファイルは不要。
**意見が分かれた・検討が必要** → `discussions/` にトピックファイルを作成 → 決定後に掲示板に転記。

## WHITEBOARD.md テンプレート

````markdown
# WHITEBOARD

## ルール
- **Goal**: {達成すべきこと}
- **関係者**:
  | 名前/役割 | エージェント名 | 担当 | 依存先 |
  |---|---|---|---|
  | {役割A} | {recipient名} | {担当内容} | {依存関係} |
  | {役割B} | {recipient名} | {担当内容} | {依存関係} |
- **接点（Connections）**: {役割間で影響し合う領域。ここに関わる発見は必ず記録}
  - {例: キャッシュ戦略 — 実装方針とテスト観点の両方に影響}

---

## 掲示板

<!-- 最新の事実・決定を追記する。日常の参照先 -->
<!-- 形式: - [役割] 内容 -->
<!-- 決定事項: - [決定] 内容（topic-XX） -->
<!-- タスク完了: - [PM] Task N 完了（担当者） -->
<!-- 文言変更: - [変更] 文言: "xxx" → "yyy" -->
````

### 掲示板の記入基準

- 技術的制約（「このAPIは非推奨」「この環境では動かない」）
- specにない前提（「既存コードはこのパターンで統一されている」）
- 手戻りにつながる情報（「この方針だと後工程で問題になる」）
- **議論で決定した事項**（決定後に必ず転記する）
- **タスク完了状況**（`- [PM] Task N 完了（担当者）`）— コンテキスト圧縮で状況を見失う対策
- **文言変更**（`- [変更] 文言: "xxx" → "yyy"`）— 全員が最新の文言を参照できるように

**重要**: WHITEBOARD.mdに「決定事項」セクションを別に作らないこと。事実と決定は掲示板に混ぜて書く。

## 議論ファイル

### いつ作成するか（トリガー）

- specにNC（未確定事項）がある場合、Phase 0で事前作成
- メンバー間で方針が分かれたとき
- 複数の選択肢があり検討が必要なとき（「アイコンはAとBどっち？」）
- specに書かれていない判断が必要なとき（「この挙動どうする？」）
- 掲示板の情報から疑問が生じたとき（「この制約、設計に影響しない？」）
- **レビューで意見が分かれたとき**（Phase 0だけでなく実装中も使う）
- **ユーザー向け文言の統一が必要なとき**

**全員一致で即決のものは掲示板に直接書けば十分。議論ファイルは不要。**

### ファイル名の規則

```
discussions/
  topic-01-icon-selection.md
  topic-02-badge-placement.md
  topic-03-delete-button-style.md
```

### トピックのライフサイクル

```
トピック発生（問いを立てる → discussions/topic-XX-xxx.md を作成）
  → 議論（各メンバーが自分の言葉で追記）
  → 決定（結論を出す）
  → トピックファイルに `## 決定` セクションを追記（ファイル単体で完結させる）
  → 掲示板に転記（WHITEBOARD.mdに1行で結論を追記）
  → 反映（担当者がspec・コードに落とす）
```

決定を修正する場合は `**決定（修正）**:` と明記し、トピックファイルと掲示板の両方を更新し、全メンバーに通知する。

### 記入例

```markdown
# トピック1: エクスポートのアイコンどうする？

- [Designer] Saveがいいと思う。既存と統一できる
- [UI/UX] エクスポートならDownloadのほうが直感的では
- [FE] どっちでも実装は変わらない

## 決定
Downloadに決定。理由: ユーザーのメンタルモデルに合致
→ 掲示板に転記済み
```

## 知見の配置ルール

retroで出た知見は性質によって配置先を分ける:

| 性質 | 配置先 | 例 |
|---|---|---|
| 最重要ルール | `CLAUDE.md`（200行以内） | コーディング規約、コミットルール |
| 詳細ルール・特定技術領域 | `.claude/rules/` | テスト規約、API設計ルール、セキュリティ要件 |
| 環境の事実・技術的制約 | `ARCHITECTURE.md` | jsdom制約、shadcn/uiコンポーネント一覧、Intlロケール差異 |
| チーム運用ルール | `team-rules.md`（このskill内） | 文言統一フロー、レビュー到着順転送、タスク中間報告 |
| 機能固有の決定 | spec内 `WHITEBOARD.md` | 削除ボタン常時表示、フォーム上部配置 |
