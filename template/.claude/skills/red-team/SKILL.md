Red-team the following artifact: $ARGUMENTS

## Step 1: 対象の特定と攻撃者の選定

### 1-1: 成果物を読む

指定されたファイルを読み、種類を判定する:
- `specs/` 配下 → spec（仕様書）
- `plan.md` → plan（設計書）
- `articles/` や `docs/articles/` 配下 → 記事・公開コンテンツ
- その他 → 汎用ドキュメント

### 1-2: 攻撃者セットを選定する

以下の5つの攻撃者ペルソナから、成果物の種類に応じたデフォルトセットを選定してユーザーに提示する。ユーザーは追加・削除できる。

| # | 攻撃者 | 何をしにくるか |
|---|---|---|
| A1 | **犯罪者** | 詐欺、データ窃取、不正取引、なりすまし |
| A2 | **悪用者** | 規約の穴を突く、ポイント不正取得、ボット利用 |
| A3 | **アンチ・批判者** | 揚げ足取り、文脈の切り取り、炎上誘導 |
| A4 | **荒らし** | スパム、ハラスメント、報告機能の悪用、他ユーザーの体験破壊 |
| A5 | **競合** | スクレイピング、内部構造の推測、弱点の分析 |

デフォルトセット:

| 成果物 | デフォルト攻撃者 |
|--------|-----------------|
| spec（ユーザー向け機能） | A1, A2, A4 |
| spec（内部システム） | A1, A5 |
| 記事・公開コンテンツ | A3, A5 |
| plan・設計書 | A1, A2, A5 |
| 汎用 | A2, A3 |

### 1-3: retroの読み込み

成果物と同じディレクトリに `red-team/retro.md` があれば読み、過去に効いた攻撃者視点・効かなかった視点を確認して選定に反映する。

### 1-4: ユーザーに提示して合意を得る

選定した攻撃者セットをユーザーに提示し、合意を得てからStep 2に進む。

## Step 2: Red Team実行（攻撃者ごとに並列サブエージェント起動）

**情報非対称 + Mental Set回避の核心。** 選定した攻撃者ごとに独立したTask toolを**並列で**起動する。各サブエージェントは互いの結果を知らず、完全に独立した思考で攻撃する。

### 1-5: 構造的前提を抽出する

成果物とARCHITECTURE.mdから、サブエージェントに渡すべき**構造的前提**を抽出する。作成経緯や設計意図は渡さないが、既存の防御策や制約は渡す。

例:
- 「認証はOAuth2で実装済み、セッション管理あり」
- 「レート制限はAPI Gateway層で適用済み」
- 「UGCはサーバーサイドでサニタイズ済み」

選定した攻撃者の数だけTask toolを並列で起動する。各Task toolに渡すプロンプト:

```
`.claude/skills/red-team/red-team-agent.md` を読み、その指示に従って以下の成果物を攻撃せよ:

対象: <ファイルパス>
攻撃者: <A1 のみ（1つだけ指定）>

構造的前提（これらは事実として扱え）:
- <抽出した前提1>
- <抽出した前提2>

攻撃シナリオは最も被害が大きいものに絞り、最大3件までにせよ。

攻撃シナリオを見つけたらテキストで返せ。以下のフォーマットで:
### RT-NNN: [攻撃シナリオのタイトル]
- **攻撃者**: <担当攻撃者>
- **重大度**: critical / warning / suggestion
- **該当箇所**: [セクション名 or 機能]
- **攻撃手順**: [具体的にどう攻撃するか。ステップバイステップ]
- **被害**: [成功した場合の被害]
- **対策案**: [こうすれば防げる]

攻撃が成立しなければ「この攻撃者視点では攻撃なし」と返せ。
```

**渡さないもの:**
- 成果物の作成経緯
- 議論ログ（discussions/）
- セキュリティ対策の意図や設計判断の背景
- 他の攻撃者の結果

## Step 3: 結果統合・偽陽性フィルタ・結果提示

全サブエージェントの結果が返ってきたら:

1. **重複をマージする**: 同じ機能・同じ攻撃手順のシナリオが複数の攻撃者から出た場合、1つに統合する。攻撃者列に全攻撃者を記載し、最も高い重大度を採用する
2. **各攻撃シナリオを再検証する**（メインコンテキストは対策の意図を知っているので判定できる）:
   - **accepted**: 対策が必要な現実的な攻撃シナリオ
   - **rejected-already-mitigated**: 既に対策済み。対策内容を添える
   - **rejected-unrealistic**: 現実的でない攻撃シナリオ。理由を添える
3. **acceptedに優先度をつける**:
   - **now**: 今すぐ対処すべき（金銭的被害、データ漏洩、法的リスク）
   - **next**: 次の作業で対処（ブランドリスク、悪用の余地）
4. **結果を RED-TEAM.md に書き出す**。出力先: `<成果物のディレクトリ>/RED-TEAM.md`
5. **結果をユーザーに提示する**: accepted の攻撃シナリオを優先度順に提示

## Step 4: Pre-Mortem（事前死亡診断）

攻撃者ごとの結果を提示した後、メインコンテキストで以下の問いを立てる:

**「リリースから6ヶ月後、この仕様は大きな問題を引き起こした。何が起きたか？」**

Step 2-3の攻撃シナリオは「今この瞬間の攻撃」。Pre-Mortermは「時間軸」を入れて長期的なリスクを探す:

- ユーザーが100倍に増えたとき、この悪用はスケールするか
- 規約や法律が変わったとき、今の設計で対応できるか
- 攻撃者のツールが進化したとき（AI自動化等）、この防御は持つか

見つかったリスクがあればRED-TEAM.mdに追記する（IDはRT-PM-NNN）。なければスキップしてよい。

## Step 5: 再攻撃（オプション、最大1回）

ユーザーが対策後に再攻撃を依頼した場合のみ実行。

- **対策後の成果物**をサブエージェントに渡す
- Round 2で打ち切り

## Step 6: Retro（振り返り）

攻撃完了後、成果物と同じディレクトリに振り返りを書き出す。

出力先: `<成果物のディレクトリ>/red-team/retro.md`

```markdown
# Red Team Retro

Date: YYYY-MM-DD
Target: [成果物のファイルパス]

## 効いた攻撃者視点

| 攻撃者 | シナリオ数 | accepted数 | 代表的な発見 |
|--------|----------|-----------|-------------|

## 効かなかった攻撃者視点

| 攻撃者 | 理由 |
|--------|------|

## 偽陽性パターン

- [非現実的と判定された攻撃シナリオのパターン]

## スキル改善メモ

- [次回以降に改善すべき点]
```
