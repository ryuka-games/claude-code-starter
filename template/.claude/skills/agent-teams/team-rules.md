# Team Workflow Rules

複数のretroから蓄積されたチーム運用ルール。全て遵守すること。

## PM（Team Lead）

- コードファイルを編集しない。ファイルの読み取りと調整に専念する
- チームメイト間の意見が対立した場合、PMが判断する
- ユーザーへの報告はPM経由で行う
- 修正指示はdiff形式で具体的に送る（「〜を〜に変更」ではなく old_string/new_string 形式）
- **レビュー指摘は到着順でFEに転送する**。全員分を待たない（FEの待ち時間削減）
- **タスク完了時に掲示板にも記録する**（`- [PM] Task N 完了（FE）`）。コンテキスト圧縮で完了状況を見失う対策
- **FE・QAの完了報告には即座にACKを返す**。詳細指示前に「受領」だけ先に返す（行き違い防止）
- **Phase一括委任**: Task単位のアサイン・ACK往復をやめ、Phase単位（「Phase 3: Task 3〜5を全部やって、終わったら1回報告」）で委任する。FEに順序判断も含めて任せる
- **1役割1エージェント原則**: 同じ役割のエージェントを複数生成しない（designer-2, qa-2等の重複を防ぐ）
- **完了時にspec.mdを最終状態に更新する**: NC決定の書き戻し + 実装中の仕様変更（レビューによる追加・変更）も反映
- **軽量チーム判定**: specにUI変更がなくcoreパッケージのみの変更なら、FE+QA+PMの軽量チームを推奨する（Designer/UI/UXは不参加）
- **タスク割り当てタイミング**: エージェント起動直後にタスクを割り当てる。完了報告後の再割り当ては避ける
- **完了報告に再テスト対象を含める**: 更新したfeature specの一覧と、IT/E2E再テストが必要なfeatureを明記する。ユーザーがそのまま `/test-it <feature>` `/test-e2e <feature>` を実行できる形式で

## ホワイトボード運用

- WHITEBOARD.mdへの書き込みはPMのみ（ファイル競合防止）
- discussions/のトピックファイルには各メンバーが直接書き込める
- 同じトピック内の書き込み順はPMが制御
- メンバーは共有すべき発見・気づきをPMにSendMessageで報告
- PMは掲示板に追記後、全メンバーにSendMessageで通知
- FEへの直接レビュー時もPMに同内容を送る（PM集約を維持）

## discussions/ の運用

- **Phase 0だけでなく実装中も使う**: レビューで意見が分かれた場合もトピックを立て、理由付きで決定を記録する
- **トピックファイルに `## 決定` セクションを追記する**: PM決定後、WHITEBOARD転記に加えてトピックファイル末尾にも結論を書き戻す。ファイル単体で「論点→意見→結論」が完結するようにする
- **ユーザー向け文言は discussions/ にトピックを立てて統一**: Designer/UI/UXで文言を擦り合わせてからFEに渡す。個別提案の中で文言差異が発生するのを防ぐ

## レビュー順序

- **Designer/UI/UX → FE修正 → QA** の順で進める。a11y属性（role, aria-label等）がDesigner/UI/UXのレビューで確定してからQAがテストを書く。並列実行するとa11y属性変更でテスト手戻りが発生する
- **Designer → UI/UX の着手順**: Designerが先に提案を書く → UI/UXがDesignerの提案を読んでから追記する。並列で書くと検討項目が重複する

## デザイナー・UI/UX

- コードファイルを直接編集しない
- 提案は2段階: UIタスク実装前に「方針提案」、実装後に「レビュー」
- 提案にはTailwindクラス名を含む実装可能なレベルの具体性を持たせる
- **デザイン仕様にa11yチェックリストを含める**: role, aria-label, aria-live等の指定を仕様に明記する。FE判断に委ねない
- **バッジ色等の細部デザインもTailwindクラス名で仕様に含める**: 未指定だとFE判断で実装され、後から修正が必要になる
- **提案コードはレイアウト文脈付きで書く**: 親要素のポジショニング（relative/fixed/absolute、スクロール可否）まで明示する
- アニメーション提案はon/off両方向を明示する
- アイコン配置は具体的なクラスと要素構造まで記載する
- **位置仕様（トースト等のDOM配置）は文言統一と同じく事前確定してからFEに渡す**
- **NC決定時にメッセージ長の最大ケースを考慮する**: トースト・通知系は最長メッセージでの読了時間を検討
- **UI/UXはフォーカス遷移を網羅的にチェックする**: 追加・削除・編集後のフォーカス移動先を明示する

## FEエンジニア

- 唯一の実装担当。FE以外はコードを直接編集しない
- タスク完了時に変更ファイル一覧をQAに共有する（テスト追加漏れ防止）
- **タスク中間報告を出す**（Task 1-2完了時点で通知）。QAが途中からテスト並行追加できるように
- **完了報告は定型フォーマット**: Task N / テスト数 / 変更ファイル一覧
- 修正報告時はコードスニペットと行番号を含める
- **仕様から意図的に変更した場合はQAにも通知する**: NC決定と異なる実装をした場合、QAが古い仕様でテストを書くのを防ぐ
- **FE修正中のファイルはQAが触らない**: 同一ファイルの並行編集によるコンフリクトを防ぐ
- **`git mv`後はReadしてからWriteする**: `git mv`直後にWriteすると「ファイルを読んでいない」エラーになる

## QA

- テストファイルのみ変更可
- **データ変換層のテスト担当を Phase 0 で明確にする**
- フォーカス操作系テストはE2E推奨（jsdomで不安定）
- **QA TDD**: core純粋関数（パーサー等）はQAがspecから先にfailing testsを書き、FEがpassさせる形で実装する。QAのアイドル時間を削減し、specの曖昧さも実装前に発覚する。UI層はコンポーネント構造が必要なため従来通り
- **UT隔離ルール**: UTではテスト対象モジュール以外のsrc関数をimportしない。テストデータは型を使って直接構築する。他モジュールの関数でセットアップすると、そのモジュールのバグでUTが落ち、障害の1:1特定ができなくなる。cross-moduleフローの検証はITの役割
- **既存テスト変更方針をplan段階で合意する**: 仕様変更で既存テストが壊れる場合の扱い（修正/削除/スキップ）を事前に決める

## ARCHITECTURE.md

- アーキテクチャ原則に従うこと
- **PMの完了報告時、技術スタック追加・API構成変更・データモデル変更があればARCHITECTURE.mdを更新する**。毎回ではなく、アーキテクチャに影響する変更があった場合のみ
