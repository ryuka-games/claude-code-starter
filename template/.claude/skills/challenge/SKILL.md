Challenge the following artifact: $ARGUMENTS

## Step 1: 対象の特定と観点の選定

### 1-1: 成果物を読む

指定されたファイルを読み、種類を判定する:
- `specs/` 配下 → spec（仕様書）
- `plan.md` → plan（設計書）
- `articles/` や `docs/articles/` 配下 → 記事ドラフト
- `ARCHITECTURE.md` → アーキテクチャ文書
- その他 → 汎用ドキュメント

### 1-2: 観点セットを選定する

以下の5観点から、成果物の種類に応じたデフォルトセットを選定してユーザーに提示する。ユーザーは追加・削除できる。

| # | 観点 | 何を壊しにいくか |
|---|---|---|
| V1 | **ユーザー視点** | 全員が理解できるか。利用者が困る場面はないか |
| V2 | **一貫性・矛盾** | 自己矛盾、用語の揺れ、暗黙の前提 |
| V3 | **なぜなぜ分析** | 根拠の連鎖が途切れてないか。「なぜ？」を掘り下げて崩れる箇所 |
| V4 | **実現可能性** | 技術的にできるか。工数・依存のリスク |
| V5 | **安全性・プライバシー** | 出して大丈夫か。漏洩・攻撃面・障害影響 |

デフォルトセット:

| 成果物 | デフォルト観点 |
|--------|---------------|
| spec | V1, V2, V3, V4, V5 |
| plan | V2, V3, V4 |
| 記事ドラフト | V1, V2, V3, V5 |
| 設計書 | V2, V3, V4, V5 |
| 汎用 | V1, V2, V3 |

### 1-3: retroの読み込み

成果物と同じディレクトリに `challenge/retro.md` があれば読み、過去に効いた観点・効かなかった観点を確認して選定に反映する。

### 1-4: ユーザーに提示して合意を得る

選定した観点セットをユーザーに提示し、合意を得てからStep 2に進む。

### 1-5: 構造的前提を抽出する

成果物とARCHITECTURE.mdから、サブエージェントに渡すべき**構造的前提**を抽出する。作成経緯や設計意図は渡さないが、データの保証や制約は渡す。

例:
- 「convert.tsが正しいツリー構造を保証する（孤立ノードは発生しない）」
- 「MAX_DEPTH=4で深さ制限済み」
- 「認証はOAuth2で実装済み」

これにより、上流の保証を知らないことによる偽陽性を削減する。

## Step 2: 反証の実行（観点ごとに並列サブエージェント起動）

**情報非対称 + Mental Set回避の核心。** 選定した観点ごとに独立したTask toolを**並列で**起動する。各サブエージェントは互いの結果を知らず、完全に独立した思考で反証する。

選定した観点の数だけTask toolを並列で起動する。各Task toolに渡すプロンプト:

```
`.claude/skills/challenge/challenge-agent.md` を読み、その指示に従って以下の成果物を反証せよ:

対象: <ファイルパス>
観点: <V1 のみ（1つだけ指定）>

構造的前提（これらは事実として扱え。これに対する指摘は不要）:
- <抽出した前提1>
- <抽出した前提2>

指摘は最も重大なものに絞り、最大3件までにせよ。

指摘を見つけたらテキストで返せ。以下のフォーマットで:
### C-NNN: [指摘のタイトル]
- **観点**: <担当観点>
- **重大度**: critical / warning / suggestion
- **該当箇所**: [セクション名 or 引用]
- **問題**: [何がどう壊れるか。具体的なシナリオ]
- **提案**: [こうすれば壊れない]

問題が見つからなければ「この観点では問題なし」と返せ。
```

**渡さないもの:**
- 成果物の作成経緯
- 議論ログ（discussions/）
- 作成者のコメントや意図の説明
- WHITEBOARD.md
- 他の観点の結果

## Step 3: 結果統合・偽陽性フィルタ・結果提示

全サブエージェントの結果が返ってきたら:

1. **重複をマージする**: 同じ箇所・同じ修正提案の指摘が複数の観点から出た場合、1つに統合する。観点列に全観点を記載し、最も高い重大度を採用する。**複数観点からの収束は信頼度が高い指標**として扱う
2. **各指摘を再検証する**（メインコンテキストは成果物の経緯を知っているので偽陽性を判定できる）:
   - **accepted**: 対処が必要な有効な指摘
   - **rejected-already-considered**: 既に検討済み・意図的な判断。却下理由を添える
   - **rejected-false-positive**: 誤読・前提の誤り。理由を添える
3. **acceptedに優先度をつける**:
   - **now**: 今すぐ対処すべき（実バグ、セキュリティ問題）
   - **next**: 次の作業で対処（品質改善、一貫性向上）
4. **結果を CHALLENGE.md に書き出す**。出力先: `<成果物のディレクトリ>/CHALLENGE.md`
5. **結果をユーザーに提示する**: accepted の指摘を優先度順に提示

## Step 4: 再反証（オプション、最大1回）

ユーザーが修正後に再反証を依頼した場合のみ実行。

- **修正後の成果物**をサブエージェントに渡す（修正前は渡さない）
- Round 2の結果も同様に偽陽性フィルタを行う
- **Round 2で打ち切り。3回目は実行しない**（3回以上は収穫逓減が激しい）

## Step 5: Retro（振り返り）

反証完了後、成果物と同じディレクトリに振り返りを書き出す。

出力先: `<成果物のディレクトリ>/challenge/retro.md`

```markdown
# Challenge Retro

Date: YYYY-MM-DD
Target: [成果物のファイルパス]

## 効いた観点

| 観点 | 指摘数 | accepted数 | 代表的な発見 |
|------|--------|-----------|-------------|

## 効かなかった観点

| 観点 | 理由 |
|------|------|

## 偽陽性パターン

- [偽陽性になった指摘のパターン。次回避けるべき傾向]

## スキル改善メモ

- [次回以降に改善すべき点]
```

### retroの活用

- **次回の `/challenge` 実行時** → 過去のretroを読み、効いた観点を優先、効かなかった観点は外すか説明付きで提示
- **スキル本体の改善時** → 複数のretroで同じパターンが2回以上出現したら、スキル本体のルールに昇格
